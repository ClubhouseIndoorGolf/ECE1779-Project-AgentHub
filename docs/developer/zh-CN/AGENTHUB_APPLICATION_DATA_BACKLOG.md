# Jinxi Hu 的 AgentHub 后端开发清单

后端已有会话和消息存储、账号权限检查、模拟退款审批，以及实时事件的保存和续传。接下来的两张 PR 分别补齐**任务结果查询**和**请求失败时的错误提示**。本清单以 2026 年 11 月 17 日的 `main`（`4e9c8c0`）为基线，数据库迁移版本为 `0007_conversation_events`。 [项目分工](../../AgentHub_Project_Proposal.md#proposed-division-of-labour) · [数据库参考](../../BACKEND_DATABASE.md)

## PR 1 让用户能查看退款检查、审批和处理结果

用户重新打开会话时，可以看到订单能不能退款、方案是批准还是拒绝，以及获批后退款有没有完成。比如，用户只问「这笔订单能退吗」，页面就显示检查结论和原因。如果退款已完成，页面还能显示实际的模拟退款金额。后端负责提供这些数据，前端接入接口后负责展示。

退款检查结果保存在 `executions` 表里。历史接口返回来源消息的 `execution_id`，前端可据此读取结构化的资格、审批和模拟退款结果。 [开发说明](../EXECUTION_DETAILS.md) · [API 示例](../../../README.md#read-a-saved-refund-result) · [执行记录模型](../../../backend/app/models.py)

### 后端实现

- [x] **让历史消息指向任务。** 在触发退款检查或审批流程的用户消息上，返回对应的 `execution_id`。这个 ID 对应数据库里已保存的执行记录。沿用现有消息分页和首屏的 SSE v2 游标。
- [x] **增加任务详情接口。** 添加只读接口 `GET /executions/{execution_id}`，返回退款资格、原因码、金额和政策版本。有审批记录时返回决定和时间。有后续任务时返回执行状态。有已保存的处置记录时返回最终结果。
- [x] **检查谁能查看。** 通过任务对应的用户消息找到会话，只有会话所属账号可以读取详情。用公开响应模型明确返回字段，订单编号和以分为单位的金额沿用现有方案接口的字符串格式。 [响应模型](../../../backend/app/schemas.py)

### 怎么验收

| 操作 | 应该看到什么 |
| --- | --- |
| Alice 只检查一笔订单能否退款，然后重新打开会话 | 根据历史消息里的 `execution_id`，可以查到原来的检查结论和原因码 |
| Alice 批准退款并等待任务完成 | 详情显示原审批决定和已保存的模拟退款结果 |
| Alice 拒绝方案，或方案过期，或获批后的后台任务失败 | 详情显示对应的决定或状态，处置结果为空 |
| Bob 用 Alice 的执行 ID 查询，或查询一个不存在的 ID | 两种请求都返回 `404` |
| 读取普通聊天和已有会话 | 历史记录和分页可正常读取。有执行记录的消息带 `execution_id`，首屏仍返回 SSE v2 游标 |

## PR 2 让前端知道请求为什么失败

这张 PR 处理两类失败。标题或正文里含数据库无法保存的字符时，接口返回 `422`。请求本身有效，但与已有提交、审批决定或方案状态冲突时，接口返回 `409`，并给出前端可以识别的错误码。

### 在写入数据库前检查标题和正文

当前输入校验会放行 NUL（`U+0000`），数据库驱动会拒绝含这个字符的文本。把检查加到标题和正文的输入模型，错误说明继续使用英文。 [输入模型](../../../backend/app/schemas.py)

- [ ] 创建会话或发送消息时，如果标题或正文含 NUL，返回 `422`，并核对数据库里没有新增对应的会话、消息或任务。
- [ ] 用中文和表情符号做回归测试，确认正常输入能保存，消息正文保留原文。

### 给不同的业务冲突加错误码

保留 HTTP `409` 和原有英文错误说明 `detail`，增加 `code` 字段。和前端确认下表中的名称和对应操作。 [提交与审批接口](../../../backend/app/main.py) · [当前页面的错误处理](../../../backend/app/static/chat.js)

| 用户遇到的情况 | 建议的 `code` | 页面可以怎么处理 |
| --- | --- | --- |
| 发送不同的正文时沿用了上一条消息的提交键 | `IDEMPOTENCY_CONFLICT` | 保留草稿，用户确认发新消息时再生成新键 |
| 会话里还有一份方案等审批，或获批后的处理尚未完成 | `CONVERSATION_BUSY` | 刷新历史，显示正在等待的步骤 |
| 用户审批时，方案已经过期 | `PROPOSAL_EXPIRED` | 刷新方案，提示用户重新发起请求 |
| 用户提交的决定与已经保存的决定不同 | `DECISION_CONFLICT` | 展示已保存的决定 |

- [ ] 测试每种冲突是否返回对应的 `409`、`detail` 和 `code`。
- [ ] 用同一个提交键和同一份正文重试，或再次提交相同审批决定，确认接口仍返回原回执。
- [ ] 在方案过期后提交审批，确认后端先保存方案失效状态和事件，再返回 `409`。 [审批集成测试](../../../backend/tests/test_resolution_workflow.py)

## 需要和队友一起验收的工作

- **和 Chengxi 验收实时更新。** SSE v2 后端已通过跨副本续传测试，浏览器目前使用 v1。Jinxi 提供 v2 的游标、事件格式和账号归属规则，Chengxi 负责浏览器升级、断线重连和重复事件处理。验收时先打开会话并记下游标，断开后批准方案，再连到另一个 API 副本。检查审批、任务进度和退款结果能否按顺序补回来。 [SSE v2 契约](../../LIVE_UPDATES.md#durable-event-replay) · [MT20 验收步骤](./MANUAL_TESTING.md#mt20-跨-api-副本续传持久化-sse)
- **和 Yuzhe、Shawn 验收云端恢复。** Yuzhe 负责 Swarm 部署和故障演练，Shawn 负责后台任务接管和模型接入。Jinxi 核对数据库迁移版本，以及故障恢复后能否找到原会话、审批回执和退款结果。同一方案应只有一笔模拟退款和一条客户回复。 [云端演练计划](../../CLOUD_DEPLOYMENT.md#safe-local-checks-and-consolidated-integration-plan) · [项目分工](../../AgentHub_Project_Proposal.md#proposed-division-of-labour)

## 团队确认后再排的工作

- **可撤销的登录会话。** 当前用 HTTP Basic 验证账号。如果验收要求服务端登出、会话到期或撤销，再实现登录会话，并约定已打开的 SSE 连接何时关闭。 [认证草案](./AGENTHUB_BACKEND_V1_SPEC.md#通用约定与认证)
- **只回复客户并关闭工单。** 如果业务范围包含无退款关单，再把客户回复和工单更新一起保存为方案，获批后执行。 [业务验收草案](./AGENTHUB_BACKEND_V1_SPEC.md#第一版验收案例)
- **任务列表和旧会话分页。** 如果前端需要在会话里按列表查看多笔任务，或需要查看超过当前列表上限的旧会话，再补对应的分页接口。
